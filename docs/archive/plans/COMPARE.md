# Shared core: Plan A versus Plan B

Compared against checkout `749d826`, [Plan A](CORE-PLAN-A-central.md), [Plan B](../../../CORE-PLAN.md), and [Konrad's latest direction](CORE-ADDENDUM.md). The 20 October 2026, 07:49 Warsaw direction supersedes A: apps must reach Hermes directly, the central service must only distribute updates, and Hermes must remain unchanged. Both plans leave Hermes unchanged; only B meets the runtime requirement.

| Area | A: central runtime backend | B: signed update service |
| --- | --- | --- |
| Server outage | New chats, approvals, team dispatch and routine-result delivery stop. Existing runs, Hermes cron and already-authorized edge queues can continue while the edge stays up. Apps show cached history and drafts. The proposed emergency route restores only Stop and decisions on pending operations. | Normal work continues with the last verified bundle; even a fresh app has an embedded baseline. Updates and revocations of update keys may be delayed. Expired update metadata warns without stopping work. Box, network and provider failures still matter. |
| Attack surface and key custody | Adds a live API, connection relay, database, workers and tenant accounts. Hermes credentials move off clients onto boxes. Device approval keys are proposed as non-exportable, user-presence-protected keys. A compromised backend can expose transcript projections, mislead users and inject chat, although properly gated operations still require box-verified approval. | Static hosting holds no runtime credentials, approvals or transcripts, and no signing keys. Clients retain each box's Hermes credential. Release keys stay with the publisher; approval keys stay on devices. A stolen release key can distribute hostile tools or prompts across the fleet. |
| Approvals and tenant isolation | Box verification, protected service accounts and a device-signed membership list aim to prevent server-forged approvals. Shared storage and routing require strict tenant checks. Membership recovery is complex; every edge restart requires an operator and an independently supplied current membership checkpoint. | Required phase adds device-signed **managed** approvals directly to each box; native Hermes approvals remain Bearer-authenticated. Device membership is enrolled locally. No central tenant runtime data exists to leak, but box/profile isolation remains necessary. Signed updates do not isolate bots sharing one operating-system account. |
| Hosting and running cost | Always-on application servers, database, encrypted backups, monitoring and outage response. The plan budgets roughly €20–35/month for a pilot and €70–150 for redundant hosting, before operational labor. | Static object storage/CDN, signing and release tooling; no runtime database or connection relay. The plan budgets €0–5/month for hosting. Release testing, key custody and box maintenance still cost time. Both plans leave model/provider costs on boxes. |
| Implementation and migration | Larger rewrite: move queues, routing, routines and policy out of Swift; add edge connections and backend state; transfer ownership without duplicate execution. Long coexistence and rollback paths. | Keeps today's connections and behavior owners. Adds verified bundles, trusted installation, an updater, approval signing and native UI rendering in stages. Smaller migration, but signature verification, version compatibility and safe application still need substantial work. |
| Future mobile app | One connection and shared server-side state simplify feature parity and coordination while the phone is disconnected. Native review/signing still needs app work. | Existing direct Hermes client remains useful. Shared UI definitions reduce duplication, but new local actions still need implementation. B does not move Mac-owned orchestration onto an always-running service or provide cross-device synchronization and push by itself. |
| Changes without recompiling | Backend deployments can change orchestration rules and compose screens using existing native components. New native components, capabilities and security protocols still require builds. | Bundles change box skills/tools, prompts, typed settings, copy and screens using existing components/actions. New app logic, Hermes API calls, native capabilities and approval protocols still require builds. Versions may differ until consumers update; some box plugin changes need an operator reload. |
| Offline and remote boxes | Outbound WSS handles boxes behind routers without inbound access. Normal control depends on reaching the backend. Box-local work can survive a partition, but edge restart gates reduce unattended recovery. | Updates need only outbound HTTPS. Runtime access still needs a working direct route to each box, such as its secured HTTPS origin or a private network. A reachable local box can work without the update host; a disconnected phone cannot control an unreachable remote box. |

Hosting figures above are the plans' unverified planning estimates, not current provider quotes. A buys centralized coordination and simpler remote connectivity at the price of a shared operational dependency. B removes that dependency for updates, but does not eliminate the work of securing and reaching each box.

The checkout supports B's smaller migration claim: `Packages/SwarmHubCore/Sources/SwarmHubCore/HermesClient.swift:121` builds direct requests and `:125` attaches the Bearer key. Today's Mac managed approvals use the same profile key for HMAC and Bearer authentication (`Sources/AgentApp/Models/ManagedRemoteControl.swift:17`, `:44`), so device signing is new work, not an existing guarantee. Skills load from packaged resources (`Sources/AgentApp/BotManager/SkillLibrary.swift:64`) and install through a manager turn (`Sources/AgentApp/Stores/AppStore+Skills.swift:82`, `:104`); B can replace this distribution path without rerouting conversations. The iOS project already links `SwarmHubCore` (`Apps/iOS/SwarmHub.xcodeproj/project.pbxproj:34`), but advertises a limited first-build feature set (`Apps/iOS/Sources/RootView.swift:74`).

B needs precise security promises. Its initial updater and trust keys must be installed outside model turns, using the operator-verified process in B §3.5; signatures alone cannot make an untrusted installer safe. Protected updater files do not protect all installed skills or mutable update records from a bot with the same account, a boundary documented today at `Resources/Skills/swarmhub-messages/SKILL.md:155`. Device signing must ship before B's config/UI rollout, with no return to shared-key managed approvals after enrollment; protection of that box-side verifier and membership state still needs qualification. Local confirmation of code updates reduces automatic fleet exposure, but does not prove code is safe, and automatically applied prompts can also alter behavior.

Both designs deliberately restrict downloaded app UI to data interpreted by compiled components. Neither promises unlimited feature changes without a build or guarantees App Store acceptance; review requirements must be checked before submission. For mobile, prioritize direct connectivity and the shared native action catalogue early: B's update service cannot compensate for missing phone features or keep app-owned automation running after the app stops.

## Recommendation

Choose **Plan B**, including its required device-signed managed approvals and protected updater installation. It follows your latest direction, keeps ordinary work available when our update service fails, and changes much less of the working product. It also avoids operating a central service that every conversation depends on. Accept that some new phone features will still need an app release, and that each remote box needs a secure direct connection; A's broader central coordination is not worth reversing your availability requirement now.

## Decisions for Konrad

1. **Who holds the update signing keys?** Options: one key on your Mac; two offline recovery/root keys stored separately plus a hardware-held publishing key; or require two people to sign every release. **Recommend the second option**, reusing B decision 1: keep recovery possible if the publishing key is lost or stolen, without requiring two people for routine releases. Keep update keys separate from app-update and approval keys.
2. **Which updates happen automatically?** Options: everything automatic; settings/UI automatic but programs running on boxes require local confirmation; or everything manual. **Recommend the middle option**, reusing B decision 2. Test releases on a small trial group first, and remember that prompts and settings still deserve review even when they install automatically.
3. **Where should updates be hosted?** Options: GitHub Releases; static storage with a CDN; or a small server we maintain. **Recommend static storage with a CDN, with GitHub as a backup source**, following B's hosting recommendation. Keep it limited to signed files, with no customer runtime data or live approval service.

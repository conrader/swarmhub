# Shared-core plan: one central backend (core4)

Baseline: detached `749d826` (`swarmhub/peer-delivery`), 2026-10-20. This comes from reading the source only: no app, test, worker, installer or service was run, and nothing was provisioned. References are repository-relative `path:line`; every reference kept from core1 was rechecked against this checkout. Inputs: `CORE-ADDENDUM.md` (Konrad, 07:19–07:20) and the core3 cross-review (lost admin device vs head journal, understated §9/§4.1 costs, text slips). **[A]** marks an assumption.

**Recommendation.** Build three layers with two narrow interfaces between them:

```
 FRONTEND  Mac app (Sparkle) · iOS app (App Store) · later Android/web
   UI only: renders server-described views, holds device keys, signs exact operations
        │  Client API v2: HTTPS JSON commands + SSE events, view documents, signed decisions
        ▼
 BACKEND   ONE central Swarm Hub server (ours)
   all behaviour: routing, gates, queues, scheduling, routines, prompts, Draft Send, view composition
        │  Box link: OUTBOUND WSS from each box, typed RPC frames, box-signed admissions
        ▼
 BOX EDGE  swarmhub-edge (our code on each box, evolved from `swarmctl control serve`)
   execution primitives + last-line verification of device signatures, no policy choices
        │  loopback only: the stock Hermes HTTP API, existing plugin hook, code-job
        ▼
 HERMES    unchanged runtime on local/remote boxes (never modified)
```

The backend decides; it does not authorize. Device-required operations are signed on the device over a hash the **box** computed, and the box verifies that signature before acting, so a compromised backend can delay or drop an operation but cannot forge, alter or replay one. Behaviour ships as backend deploys; clients render server-described views with a fixed native component set, so only new components or native capabilities need a client build.

## 2. Layer interfaces

### 2.1 Frontend ↔ backend: Client API v2

- Transport: HTTPS JSON for commands and queries, SSE for events (with cursor resume and a snapshot when the cursor has expired), and APNs wake hints with no payload authority. Clients keep v1's discipline: no redirects, no URL credentials, `no-store`, ephemeral sessions.
- Client auth: a per-device session credential (OAuth-style refresh token in the Keychain, no user presence) for reading and chatting, separate from the **signing key** (§3). Clients never hold Hermes `API_SERVER_KEY`s again; those stay on the box.
- Resources: tenant, boxes, profiles, conversations/messages/runs, operations (managed actions, approvals, secret requests), routines/results, policy, devices, **views**. Pagination is required.
- Commands carry `{request_id (idempotency), resource, expected_revision, typed payload}`. The same key with the same payload returns the original receipt; the same key with a different payload is a conflict. Admission is a different event from completion, and a missing receipt never counts as success. Error codes: `unauthenticated`, `forbidden`, `stale_operation`, `unsupported`, `expired`, `box_offline`, `unknown_outcome`.
- Events: `{schema, tenant, seq, event_id, resource, revision, type, payload}`, committed in the same transaction as the state change (outbox). Streaming deltas are for display only; durable terminal records decide completion (do not infer it from EOF or `[DONE]`). A client disconnecting never stops a run; Stop is its own command.
- `GET /v2/capabilities` returns protocol range, UI catalogue range, per-box features and auth mode. An unsupported feature is shown as disabled with a reason; it is never emulated by sending a prompt.

### 2.2 Backend ↔ box: the box link

- **The box dials out.** `swarmhub-edge` keeps one WSS connection to `wss://core.<domain>/v2/box` over 443 and needs no inbound port, no reverse-proxy route and no public Hermes origin. It handles boxes behind NAT, home Macs and laptops, and hosted VPSs the same way. Reconnects use jittered backoff and resume from the last acknowledged frame on both sides.
- **Edge = evolved `swarmctl control serve`.** Keep `swarm_control` and its modules (store, jobs, delivery, intake, teardown) as the edge's execution library. Replace the loopback HTTP listener with the outbound client, keep v1 serving available for legacy clients during coexistence (§8), and run it under a dedicated service user, not the bot's account (strict mode, §3.6).
- **Enrolment.** (1) An owner device asks the backend for a one-use code (10 min TTL); this code only correlates requests and grants no trust. (2) The operator runs `swarmctl edge enroll <code>` on the box. The edge generates an Ed25519 box key (service-owned file, 0600), an X25519 intake key and a fresh pairing nonce, then sends public keys with box facts (Hermes version, profiles, OS). (3) The backend proposes a box ID and tenant binding. (4) Through a local console or independently authenticated SSH session, the operator imports the first admin public key directly from the owner's native device UI and confirms its full SHA-256 fingerprint on the box. The device independently checks the box/intake key fingerprints from that console. Both sides confirm the same `{domain:"swarmhub/v2/pair", tenant, box_id, box_pubkey, intake_pubkey, admin_pubkey, recovery_pubkey_hash, epoch, pairing_nonce, recovery_generation, roster_version, roster_head_hash}`; the device signs it and the edge verifies against the locally pinned admin key, consumes the nonce and persists the binding. The initial roster must match that confirmed head (§3.2). A backend-supplied self-signed roster, TLS pin or enrolment code can never install or replace this trust anchor. Until the ceremony completes, only untrusted status is available; no Hermes commands or device-required operations. The edge pins the backend's TLS SPKI from the enrolment response, with one rotation pin, for transport only.
- **Pairing assumption and cost [A].** The owner device/native UI and the operator's console path are trusted independently of the backend; SSH host identity must already be verified outside it. This reciprocal console ceremony prevents first-key substitution without trusting the relay. It costs manual access and fingerprint confirmation for every box, including remote boxes; there is no unattended first pairing. For later boxes, import the existing tenant's current checkpoint and verify its chain to the pinned first admin key, rather than create another genesis; a current admin verified through that chain signs the pairing transcript if the first admin has been revoked.
- **Link auth.** Normal WebPKI TLS, plus the box signing a per-connection challenge. The backend rejects unknown, revoked or wrong-tenant boxes. A stolen box key is revoked through the roster.
- **Frames.** Backend→edge: `{cmd_id, kind, profile, payload, auth?}` where `kind` is a closed list: `chat.create/send/steer/stop`, `sessions.list/messages`, `jobs.list/create/pause/run` (stock Hermes jobs API), `action.admit/decide/execute/stop`, `approval.native.resolve`, `secret.deliver`, `policy.snapshot`, `skills.install`, `status`. There is no raw shell and no generic HTTP proxy to Hermes. Edge→backend: acks, admissions (box-signed), stream deltas, terminal results, receipts, health. The edge dedupes `cmd_id` in its existing SQLite (`swarm_store.py:56`) and returns the original receipt on a retry.
- **Hermes calls** stay loopback with the profile key that already lives in the profile's `.env` (`Resources/BotManager/manager-hermes.md:12`, `:14`). Endpoints are those the clients already use (`HermesClient.swift:41`–`:112`, `HermesJobsClient.swift:129`). Hermes source, plugins API and routes are untouched. The peer hook stays a Swarm Hub plugin registered through Hermes' extension point (`peer-runtime.py:381`).
- **Policy at turn time.** The in-turn hook cannot wait on the network, so the backend pushes a revisioned `policy.snapshot`, which the edge stores. If the snapshot is older than a TTL and the backend is unreachable, the hook **holds** held/priority deliveries instead of guessing.

### 2.3 Edge ↔ Hermes: unchanged

Everything below the edge stays as shipped: Hermes HTTP API on loopback, Hermes cron for native routines, the `peer-runtime` plugin, `code-job` with its isolation/teardown suites. The edge is the **only** caller of Hermes in the new design. Where the stock API lacks a needed guarantee (for example, an immutable single-use native approval request ID), that capability is disabled. Hermes is not patched.

## 3. End-to-end device signing (server cannot forge)

### 3.1 Threat model

The backend is trusted for availability and for orchestration, and it is assumed compromisable. It must not be able to: approve or deny a device-required operation; change an operation after review; replay an old approval; add a device or box to a tenant; or read a released secret. It **can** delay, drop or reorder traffic, show stale views, and (an inherent limit, stated plainly) inject chat text into bot conversations. So any side effect that matters must be a gated operation, not a chat instruction. Optional hardening: devices sign every user message with a non-presence key, and the edge rejects unsigned user turns on strict boxes (**[A]** cost/benefit to be judged after phase 5). Root on a box and unmanaged bot tools stay out of scope, as today (`M/SKILL.md:155`).

### 3.2 Trust roster (the anchor the server cannot write)

- The tenant **roster** is an append-only, hash-chained log of entries (`device add/revoke`, `box add/revoke`, `role change`). Every signed entry binds `{tenant, recovery_generation, version, previous_head_hash, change}`; versions increase by exactly one. Its signer must be an admin in the preceding committed roster. Entry 0 is signed by the first device, whose key the box independently pinned through §2.2, and names the offline recovery public key whose hash the pairing transcript also carries; self-signature alone is never bootstrap authority.
- The backend stores and relays the roster but cannot extend it. Every edge keeps its own copy, verifies the chain from that anchor, and only accepts device signatures from keys current in its verified roster. Devices also verify it. Chains are ordered by `(recovery_generation, version)`. Reject lower positions, different hashes at the same position, gaps and forks; an old admin cannot authorize a new branch from an obsolete head. The only permitted fork is a recovery entry (below).
- **Latest-head authority [A].** Maintain an owner-controlled, durable tenant head journal, replicated on **every current admin device** (this-device-only storage, excluded from device backups), outside **all box and backend restore sets**, with no backend write access. This is a required implementation qualification, not an ordinary backed-up roster cache. Every membership change (including recovery-key use) must atomically append its signed entry against the current head on every replica of the admin set it leaves behind (a revoked admin's replica is excluded by that same entry), each replica acknowledging with its device signature, before publication or acknowledgement as committed; competing/stale appends or a missing replica acknowledgement fail, and the change stays uncommitted. Replica messages may travel through the backend, which can delay them but not forge or merge them. The journal retains the chain and a device-signed checkpoint `{domain:"swarmhub/v2/roster-head", tenant, recovery_generation, version, head_hash}`. Moving or recovering this journal must preserve its latest head without rollback; if that cannot be proven, authority remains disabled. **[A]** The owner can retain this independent state and serialize roster changes through it; a signature or timestamp on a backend-provided checkpoint is not evidence that it is latest.
- **Edge checkpoint and restore gate.** Before accepting authority at every edge start (including restore/replacement), require an operator to transfer the journal's *current* checkpoint over the trusted console path in §2.2, bound by an admin signature to a fresh edge challenge, box ID and operation epoch. Verify the chain from the pinned anchor, the checkpoint signer against the roster at that head, and the head against the operator-imported journal value. Persist the accepted version/hash before enabling decisions. A backend replay cannot satisfy this independent head check, even if signed by a formerly valid admin. The gate runs on every start so an undetected snapshot restore cannot bypass it. Missing journal, unavailable operator, stale/reused challenge, incomplete chain or uncertain freshness means read-only status and no authority, including execution from restored queues. **[A]** Operator-assisted restarts are acceptable initially; automatic freshness would require a separately qualified, independently authenticated journal channel (candidates in §9, decision 1).
- **Revocation delivery.** Running edges persist each verified head before acknowledging it and re-check membership before committing new decisions. Show a revocation as effective on a box only after its head acknowledgement; withheld delivery/offline boxes remain explicitly pending, never reported as revoked successfully. Their next start must pass the independent latest-head gate, even if they never received the revocation before the restore. This distinguishes delayed revocation delivery from rollback protection.
- Device keys: Secure Enclave P-256 with access control requiring user presence for every signature ([Apple: Secure Enclave](https://developer.apple.com/documentation/Security/protecting-keys-with-the-secure-enclave), [`.userPresence`](https://developer.apple.com/documentation/security/secaccesscontrolcreateflags/userpresence)). Keys are not exportable and not synced. Macs without a Secure Enclave can read and chat but cannot approve, unless an equivalent store is qualified. There is no silent software fallback.
- **Lost admin device, ≥2 admins (normal case).** Because every commit needs every admin replica, each surviving admin device holds the latest head. A survivor signs restart checkpoints for the operator and commits `device revoke` for the lost device without it. No re-pairing, no recovery key. A stale journal taken from the lost device cannot pass: its key is revoked at the survivor's head, and the operator transfers only the survivor's checkpoint. Cost: every roster change needs all admin devices present, with user presence on each. **[A]** Konrad keeps at least two admin devices; with only one, every loss is the recovery case below.
- **Lost last admin device (or every journal replica): recovery key.** Until recovery, running edges keep accepting current non-admin approvers, but roster changes are refused and any edge that starts stays read-only (no head can be proven). The offline recovery key (printed/stored by Konrad, its hash pinned at pairing) re-establishes the head in four steps, without needing the lost latest head:
  1. On a new admin device, the owner gathers the highest chain available from any source (backend copy, an edge's persisted head read over the console, a surviving approver device). This is the *base*, used for audit only: it may be stale, so recovery does not depend on it being latest.
  2. The recovery key signs one entry `{domain:"swarmhub/v2/roster-recover", tenant, recovery_generation: g+1, version: 0, base_version, base_head_hash, members, next_recovery_pubkey_hash}`. `members` is the **complete** membership (the new admin key, each device and box key kept, roles); every key it omits is revoked, including any revoked after the base that the base still lists. It names the next recovery key, so a used kit cannot sign generation g+2.
  3. A fresh journal starts on the new admin device(s) with this entry as its head.
  4. Each box passes the restart gate above once, over the console. The edge verifies each recovery entry after its persisted generation in order, each against the recovery hash pinned by the generation before it (so no generation is skipped), verifies the checkpoint signed by an admin in `members` against its fresh challenge, persists the result, then installs `members`. An edge that first receives the recovery entry through the backend applies its revocations immediately and goes read-only until gated, because that only removes authority.
- **Replay after recovery.** Every edge that accepted generation g+1 rejects any generation-g chain (a higher g-version included), any earlier recovery entry, and checkpoints from the lost journal. An edge restored from a pre-recovery snapshot cannot be revived by a backend replay: the gate demands the operator-transferred current checkpoint, which carries generation g+1. At recovery the edge cancels pending admissions and queued, unexecuted operations not re-signed under `members`, because pre-recovery decisions from a possibly stolen device cannot be told apart. Fail closed: a missing or mismatched recovery hash, a generation skip, an incomplete `members` or a persistence error means no authority.
- **Recovery UX cost.** One console visit per box (pairing-like). Every omitted device is re-added by the new admin. Pending work is dropped and re-requested. Approvals are off on each box until its gate passes, and a new recovery kit must be printed and stored. Boxes the operator cannot reach stay read-only. Boxes that never see the recovery entry still trust the lost device (Secure Enclave keys need user presence) and are shown as recovery-pending, never as recovered. An offline recovery-kit *copy of the journal* is stale by construction and is never used as freshness evidence; the kit holds only the recovery key, tenant ID and anchor fingerprints. **[A]** Konrad accepts holding one.

### 3.3 Operation hash binding

1. The backend asks the edge to `action.admit` a fully resolved spec. The spec freezes argv, cwd, model/order, verifier, recipient/body, the FAKE flag, attachment hashes and the secret-handle version. Today order/model are resolved only at launch (`swarm_jobs.py:84`); v2 freezes them before signing.
2. The edge validates the spec with the existing `validate_spec` (`swarm_policy.py:159`), computes `op_hash = SHA-256(JCS(spec))` ([RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html), with cross-language test vectors), creates a fresh nonce and stores the record. It returns a **box-signed admission** `{box_id, epoch, profile, op_id, op_hash, gate, decider_role, nonce, expires}`.
3. The device fetches the full spec and the admission, checks the box signature against the roster, recomputes `op_hash` from the spec, and only then opens the native review (§5.4). It signs `{domain:"swarmhub/v2/decision", tenant, box_id, epoch, profile, op_id, op_hash, gate, decision, nonce, issued, expires, device_key_id}`.
4. The backend relays the signature. The edge checks: the signature is valid, the key is current in the roster with the required role, the `op_hash` matches the stored record, the nonce is unused, it is not expired, the status is still pending, and the epoch is current. Then, in one SQLite transaction, it consumes the nonce, records the decision and receipt, and queues execution. `run_action` (`swarm_jobs.py:111`) re-checks the committed authorization before any side effect.

### 3.4 Replay protection

The nonce is box-issued and single-use (consumed in the decision transaction), with a 60 s default TTL like v1. Expiry is re-checked after taking the lock. Epochs change on box restore or replacement, invalidating old operation challenges. **Changing the operation epoch does not establish current membership or prevent roster rollback.** Before serving authority, the edge must pass §3.2's independent latest-head gate; backend roster resync alone is insufficient. Thus a valid pre-revocation roster cannot reactivate a revoked key after restore, even to sign a fresh challenge in the new epoch. The same signed decision sent twice returns the original receipt; an opposite decision on the same op from a second device gets `stale_operation`. Receipts are box-signed, so a client can prove which decision the box committed.

### 3.5 Secrets

The device encrypts the value with HPKE ([RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html)) to the box's roster-listed intake key. It signs `{op_hash of the consuming operation, handle_id, handle_version, ciphertext_digest, intake_key_id}` with user presence. The backend sees only ciphertext, keeps it no longer than the handle TTL, and never writes it to logs or events. The edge decrypts only after verifying the signature, writes the value with the existing `write_private` (`swarm_intake.py:27`) or passes it on stdin, and deletes it under the handle's retention rule. Raw secret hashes are never exposed. A swapped value, recipient or operation needs a new handle and signature. The box that receives plaintext must be trusted with it. **[A]** Konrad allows explicitly released secrets to reach a remote box. If he does not, those operations stay unavailable.

### 3.6 Native Hermes approvals and the host boundary

Native approvals go through `approval.native.resolve` on the edge. The edge hashes the full pending tool operation it reads from Hermes, signs it as an admission, and forwards the decision only if the request is still the same one. If stock Hermes does not provide an immutable, single-use request ID, approving is disabled for that capability. Strict mode (needed before end-to-end claims are made for a box): the edge's code, SQLite, roster and keys belong to a service user that the bot's account cannot write; bot-side scripts keep admission via a restricted socket but lose `decide`; the old `swarmctl decide` with `HERMES_HOME` (`M/SKILL.md:129`, `swarm_policy.py:312`) is refused on strict boxes.

### 3.7 Fail closed

The operation stays unexecuted (pending, or explicitly failed) on any of: user cancels authentication, expired nonce, revoked or unknown key, unpaired trust anchor, roster fork/rollback or unproven freshness, spec/policy/recipient/key-version change, bad signature, backend unreachable, box offline, clock outside tolerance, unknown backend outcome, missing exact binding, or a storage error. No reviewer model, backend rule, shared bearer key, local CLI or "always allow" setting can bypass a device-required gate.

## 4. Availability, isolation, data

### 4.1 Single point of failure and degraded behaviour

| Failure | What keeps working | What stops | User sees |
| --- | --- | --- | --- |
| Backend down | Runs already in flight on boxes; jobs already queued on an edge (decision already committed there) **while that edge process stays up**; Hermes cron routines; the peer hook while its policy snapshot is fresh; box-local `swarmctl stop` for the operator | New chats, group rounds, team dispatch, routine result delivery, new approvals. A box reboot, edge crash or restart halts that box's queued jobs (read-only) until an operator passes the §3.2 freshness gate; the console gate works without the backend | Clients show "core unreachable", a read-only cache, local drafts; a restarted box shows "waiting for operator". Optional emergency lane (decision 2) |
| Box offline | Other boxes; backend queues commands for that box with a TTL | Anything on that box; device decisions for it expire, never auto-replay. If it went down by reboot or crash, it returns read-only until the §3.2 gate | Box marked offline, queued items with expiry; then "waiting for operator" |
| Client offline | Everything server/box-side under already-granted authority and explicit goal/loop budgets | Device-required steps wait | On reconnect: fresh challenge, re-authenticate |
| Partition backend↔box mid-run | The edge keeps the run and buffers events (bounded) | Delivery of results until the link resumes | Run marked `unknown` until the edge reports. Ambiguous side effects are never re-run |

Targets **[A]**: RTO 15 min and RPO ≤ 5 min (Postgres WAL/PITR) for the single-region setup. The backend stores no authority (the roster and nonces live on the edges), so a backend restored from backup cannot approve anything. At worst it re-shows stale views, which the edges reject.

### 4.2 Multi-tenant isolation

- Tenant = account. Every row and key carries `tenant_id`. Postgres row-level security sets the tenant per connection from the authenticated principal, and the query layer filters again (defence in depth).
- A box credential is bound to one tenant and one box ID. The connection hub routes a command only to sockets whose authenticated box is in that tenant's roster, and events are partitioned per tenant (no shared topics). A box cannot address another box. Cross-box delivery inside a tenant goes through the backend, and the receiving edge applies its own policy and signature checks.
- Within a tenant, roles (`admin`, `approver`, `member`, `viewer`) are roster entries, so the backend cannot escalate them. Display names are never identities: use `(box_id, profile, resource_id)`. Quotas per tenant and per box (requests, streams, storage) stop one tenant starving others. Tests: cross-tenant fuzzing on every endpoint, plus attempts to substitute a box key or socket.

### 4.3 Data at rest

| Data | Where | Protection / retention |
| --- | --- | --- |
| Transcripts | Hermes on the box is the source of truth. The backend holds a projection for history/search | Disk encryption + a per-tenant data key (envelope, KMS or file-based KEK **[A]**); projection TTL configurable; deleting a tenant deletes its keys |
| Operations, receipts, roster copy, audit | Backend (append-only) and edge (authoritative) | Signed records; the audit log is never edited; kept ≥ 1 year **[A]** |
| Secrets | Never at rest on the backend; ciphertext only in transit, ≤ handle TTL | Plaintext only on the edge, owner-only file or stdin, deleted per handle |
| Hermes keys, provider credentials | Box only (`.env`, 0600) | Taken off clients; never sent to the backend |
| Device signing keys | Secure Enclave | Not exportable |
| Backups | Encrypted object storage, separate credentials | 30-day PITR **[A]**; restore drill each quarter |

## 5. Server-driven UI

### 5.1 Model

- The backend sends **view documents**: versioned JSON trees of components from a fixed native catalogue, plus **actions** referring to backend commands. Clients render them generically and keep no behaviour of their own: a button posts `{action_id, view_id, view_rev, inputs}`, the backend decides, and an updated view comes back as an event.
- Catalogue v1, the minimum to replace today's card behaviour: `text` (plain/markdown subset, no HTML), `badge`, `key_value`, `list`, `card`, `form` with typed fields (`text`, `multiline`, `choice`, `toggle`, `date`, `schedule`, `file_pick`), `button` (`style`, `action_id`, `confirm` text), `flow` (steps with back/next), `progress`, `diff_preview`, `secret_entry` (native sheet, §5.4) and `operation_review` (native, §5.4).
- What this covers: approval and Draft cards (today `S/Views/MarkdownContent.swift:100`, `S/Models/ChatCards.swift:16`), routine result cards, routine create/edit forms (replacing client-side `RoutineSchedule` parsing), manager-op results (replacing `SwarmhubBlock` parsing on the client), connect-box and onboarding flows, team/workflow status, and policy/settings panes.
- Precedent in the code: managed records already arrive as full-spec JSON and are shown field by field (`S/Models/ManagedControl.swift:66`–`:80`), and the fence is "only a notification" (`S/Stores/AppStore+ManagedActions.swift:17`). SDUI turns that one case into the general pattern.

### 5.2 What ships without a build vs what needs one

Server-side: new card types made from existing components, text/copy, form fields, flow steps, validation messages, routing/gate/scheduling/reviewer rules, prompts and manager recipes, Draft Send semantics, team policy, and feature flags turning on server features the client can already render.

Needs a build: a new component type; a new native capability (camera, files, notification categories, widgets, Shortcuts); signing/crypto/roster changes; navigation shell; performance-sensitive views (chat transcript scrolling stays native, fed by data); accessibility or layout fixes inside a component.

### 5.3 App Store limits

- iOS App Store Review Guideline 2.5.2 forbids downloading or executing code that adds or changes features. View documents are **data** rendered by compiled components, the common server-driven-UI pattern Apple accepts. Rules: no JS/WASM/Lua interpreter, no `JSContext`, no dynamic library or bytecode loading, and the catalogue cannot express logic (no expressions or loops; conditions are evaluated by the backend). **[A]** Wording checked against the guidelines as known in mid-2026; re-read the current text before submitting.
- Guideline 2.3.1 (no hidden features): when new user-visible capabilities ship server-side, describe them in the review notes for the next build and keep the demo/review tenant at feature parity. Do not use SDUI to switch on, after review, something reviewers could not see (for example, real outbound sending).
- The Mac app ships via Sparkle (`Package.swift:11`), so App Store review does not apply, but notarization does. Apply the same discipline anyway so both clients render the same documents.

### 5.4 Security of server-driven UI

- A malicious backend controls what the user sees, so **what is signed is never server-described**. `operation_review` is a native, non-customisable component: it renders the box-signed spec (every field, destination, FAKE/real, argv boundaries, as `ManagedControl.swift:66` does today) from the admission it verified, and only it can call the signing key. A server button can only say "open review for op X". The server's summary text appears next to it, labelled as unverified.
- `secret_entry` is native too: it encrypts to the roster intake key and never reports the plaintext back to the view tree.
- Hardening: only HTTPS URLs on an allowlist, opened after confirmation; no server-supplied deep links into signing; size and depth limits on documents; strict decoding (unknown required properties make the view fail, with a visible error); server strings shown as text, never as markup; no server control over Keychain, files or notifications beyond declared, typed actions.

### 5.5 Versioning and compatibility

- Two independent version numbers: `api/2.x` and `ui/1.x`. A client sends `ui_catalog=1.3, app=0.6.2, platform=ios` and the backend composes for that catalogue. Each component declares `since`. For a component the client cannot render, the backend sends a `fallback` (text + "Update the app"). A view marked `critical` is replaced by "update required" instead of being shown partially.
- Additive changes only within a major version; a major bump keeps the previous version served for ≥ 2 client releases **[A]**. `min_client` per feature blocks clients known to be broken. A kill switch per view type turns it off quickly.
- A shared conformance suite (golden view documents → snapshot tests on Mac and iOS, decoding fuzz) lives in the repository, next to the existing fixture style (`Tests/Fixtures/remote_approval_protocol.json`).

## 7. Per-box core (brief comparison)

The core1 plan put a full core on each box. Compared with this plan:

| | Central backend (this plan) | Per-box core (core1) |
| --- | --- | --- |
| Behaviour updates | One deploy | Upgrade every box, version skew |
| Cross-box orchestration | Native | Explicit box-to-box delivery contracts |
| Inbound exposure | None (boxes dial out) | Each box exposes HTTPS |
| Client credentials | One session per device; Hermes keys stay on boxes | A key per box on every client |
| Backend outage | Orchestration pauses (§4.1) | No shared dependency |
| Trust | Needs roster + box-side verification so the server cannot forge | Box is the authority |
| Ops cost | One service to run (§6) | Nothing central, N installs |

The per-box design is more robust to outages. It loses on Konrad's main goal (one place to ship behaviour) and on credential spread. Its strongest idea (the box as last-line verifier) is kept in the edge.

## 9. Top 3 decisions for Konrad

1. **Who can grant authority: device-signed roster or server accounts?**
   (a) Server-managed accounts and devices: simplest, but whoever controls the backend can approve anything. (b) A device-signed roster that edges verify, with an offline recovery key. (c) (b) plus signed user chat messages.
   **Recommend (b).** It is the only option that meets "the server can't forge". It costs one console pairing ceremony per box and device, plus a recovery key you keep. It also costs an operator plus an admin-signed current head (over the console) on **every** edge restart, reboot or crash before that box regains authority, and a head journal replicated on every admin device, so every roster change needs all admin devices present. Keep two admin devices: losing one is then a revocation. Losing the last one is a recovery-key ceremony with a console visit per box (§3.2). **[A]** Cheaper freshness, not yet qualified: (i) automatic restart freshness from a quorum of current admin devices, each signing its journal head against the edge's fresh challenge through the backend relay (removes the console step, but needs admin devices reachable at every restart); (ii) a hardware monotonic counter (TPM/Secure Enclave-backed) binding the edge's persisted head, which covers restarts and snapshot restores but not box replacement. Neither is assumed by this plan. Revisit (c) after phase 5. Sub-decision: allow explicitly released secrets to reach a remote box as plaintext for the exact reviewed use. Recommend **yes**.

2. **What happens when the backend is down?**
   (a) Hard dependency: read-only cache, wait. (b) A narrow emergency lane: clients reach the edge directly (LAN, or the existing v1 HTTPS route) only for **Stop** and **signed decisions on already-pending operations**, with no new behaviour. (c) A full direct fallback to Hermes, as today.
   **Recommend (a) for phases 1–4, then (b), behind a per-box toggle.** (c) brings back behaviour in the clients and is the thing this plan removes. Start with hosting option A and move to B (§6) before phase 5, when chat depends on the backend.

3. **Where does data live, and on what stack?**
   (a) Backend stores full transcripts (simplest search/sync, largest breach impact). (b) Boxes stay the transcript source of truth; the backend keeps an encrypted per-tenant projection with a TTL. (c) No transcript storage on the backend at all (pure relay, no offline history).
   **Recommend (b) on an EU-hosted Python backend (§6), reusing the `swarm_*` modules.** This limits what a backend breach exposes, keeps Hermes authoritative, and moves the existing tested code instead of rewriting it.

- Boxes can run a supervised outbound service as a separate user (systemd/launchd). Installed Hermes, skill and proxy versions on real boxes were not inspected.

- App Store guideline wording, Secure Enclave availability on target Macs, HPKE/JCS library choice, and prices are to be checked before building or buying. Figures in §6 are rough list-price estimates.

# uistub1: native UI acceptance stub mode

Implemented in this worktree on `swarmhub/uistub1`, base `843024b`. No commit was made. Hermes and bundled runtime scripts were not modified, and no real connectors, remote Mac, keys or external sends were used.

## What changed

- `SWARMHUB_UI_ACCEPTANCE=1 ./scripts/run-ui-acceptance.sh` selects a DEBUG-only SwiftUI acceptance scene before constructing normal app state. The script requires explicit opt-in and builds debug. The release entry point refuses any acceptance request before constructing normal app state. Missing/invalid launcher opt-in, conflicting configuration and unsafe app dependencies fail closed with exit 78 and a payload-free diagnostic.
- Every launch creates a fresh mode-0700 `swarmhub-ui-acceptance-*` OS temporary directory. AppStore/defaults/SQLite data stay there. There is no production state import, discovery, updater or normal settings scene. The banner is exactly `ACCEPTANCE MODE - nothing is sent`.
- The scene uses the existing `ApprovalCard`, `SecretEntrySheet` and `MarkdownContent` Draft card. It adds tabs, fixture reset controls, operation details and visible receipts. **Decline** is the existing card's deny control.
- Managed and remote fixture cards are constructed from fake `ManagedRecord`s. The normal AppStore decision/reconciliation path queries the in-process fake, validates the task/fingerprint/gate/decider and exact remote origin/runtime/profile binding, and removes only the confirmed card. The remote `https://acceptance.invalid` origin is display/binding data, never a transport destination. Approving does not execute an operation.
- Secure-sheet save uses the existing `MemoryKeyStore`, with acceptance-specific copy and keyboard focus. The dummy value goes to neither Keychain nor a file, chat message or log. The sheet clears its field; the memory store disappears when the process exits.
- Draft Send still performs the normal source-message/card/target validation, then records the exact synthetic draft directly in the fake. An exclusive, fsynced mode-0600 `send-<UUID>.json` receipt records `simulated:true, delivered:false` before the card is marked handled. Errors keep the card unsent; duplicate or changed attempts cannot forward to a provider. The UI shows both flags and disables Send for a handled card.
- Acceptance startup validates the concrete fake backend and memory-key-store types, isolated store parent/defaults, absence of Hermes/configured connectors, and disabled discovery. AppStore refuses normal dependencies; backend and managed-control selection cannot fall back to Hermes. Existing QA-style guards reject all HTTP including loopback, live key/state/external-open access, Composio requests and voice launches. No listener or Hermes gateway is created.

New implementation: `Sources/AgentApp/UIAcceptance/` (three files). Integration changes are limited to launch selection, the existing guard entrypoints and the three native UI action paths. All changed/new deliverable files are below 500 lines.

## Limits and Mac handoff

Run `swift test --filter UIAcceptanceTests` and the full `swift test` suite on a Mac, then follow `ACCEPTANCE-CHECKLIST.md`. Check keyboard/mouse behavior, light/dark appearance, private receipts, restart isolation, release refusal and ordinary launch without the opt-in. This implementation has not received a native compile or visual acceptance pass on Linux.

This is a constrained native component acceptance scene with an in-process backend. It does not certify the entire normal workspace, deployed remote approval authentication/TLS/receipt recovery, Hermes orchestration, real provisioning or real delivery. Each launch starts fresh; synthetic send evidence stays in its temporary directory, while keys and fake runtime records are not restored. Build dependency fetching belongs to the normal build step; an offline build needs dependencies cached. The running scene has no network dependency. The guards follow existing app-level QA patterns and are not a claim of an OS sandbox against arbitrary injected code.

## UISTUB2: Mac build fix and review minors

**What changed** (uncommitted on `af1153e`):
- `UIAcceptanceApp.init`: this was the Mac `swift build` error. The throwing controller construction now runs in a `do` that assigns a local `let made`, and the `catch` calls `UIAcceptanceMode.refuse` (`-> Never`, exit 78). Only then does `_controller = StateObject(wrappedValue: made)` run, so the `@autoclosure` holds no `try` and the `catch` can be reached. This is the same shape as `QAApp.init`, which already compiles.
- `AppUpdater`: in acceptance mode it now says "Updates are disabled in UI acceptance mode." QA mode keeps its own message.
- `UIAcceptanceTests.approvalVariants…`: the fixed 100 × `Task.yield()` loop is replaced by the shared `waitUntil { !…managedDecisionsInFlight.contains(card.id) }` from `TestSupport.swift`. It waits on the condition with backoff, the ceiling only bounds a real hang, and it throws `WaitTimeout` instead of passing silently.
- `SecretEntrySheet.acceptance`: explicit `return` in both `#if` branches. I added this to be safe: the implicit return over `#if` may well compile, but I couldn't confirm that.

**Spots checked for the same pattern or Swift 6 strict-concurrency problems** (all Swift files in `843024b..HEAD`, read by hand):
- `try` inside an autoclosure: the only `StateObject(wrappedValue: try …)` was the one fixed. The other `StateObject(wrappedValue:)` sites in `Sources` get plain values. `TestRunGuard.refuses(_: @autoclosure)` callers pass plain strings.
- `UIAcceptanceMode`: `static let requested`, `banner` and `variable` are Sendable `let`s on a nonisolated enum. `refuse` returns `Never`. The enum, `UIAcceptanceError` and `banner` all compile in release, and the release launcher and `SecretEntrySheet` use them there.
- `UIAcceptanceIsolation`: `@MainActor`, so its mutable `static var directory` is isolated. Its callers (`UIAcceptanceController.init`, `AppStore.init`, `UIAcceptanceApp.init`, tests marked `@MainActor`) are all on the main actor. The `mkdtemp` buffer closure uses an inferred `inout` parameter.
- `UIAcceptanceRequestGuard`: `URLProtocol, @unchecked Sendable`, the same as `QARequestGuard`. The nonisolated `TestRunGuard.guarded`/`sharedSession`/`allows` read only `requested`.
- `UIAcceptanceChatBackend`: a Sendable struct. The protocol requirements it doesn't implement (`sessionTransport`, `loadMessages`, `createSession`, `stopTarget`, `requestStop`, `resolveApproval(_:approved:)`, `features`, `steer`, `forkSession`, `recentMessages`, `runStatus`, `currentRunID`) all have defaults in the `AgentBackend` extension.
- `UIAcceptanceController.init`: it touches no `self` before its five stored properties are set. The `managedControl` closure is typed `@MainActor (…) async throws`, so the synchronous call to main-actor `fake.control` inside it is legal.
- `UIAcceptanceBackend`: checked against the declarations of `ManagedRecord.Spec(kind:bot:intent:to:text:fake:)`, the memberwise `ManagedRecord(…decided_by:decided_at:)`, `RemoteBinding`/`RemoteReceipt` (Equatable), `awaiting`, `confirms`, `request(botID:) throws`, `MemoryKeyStore.setKey`, and `QAMode.writePrivate`. The local `Decision: Decodable` is decoded synchronously on the main actor.
- `AppStore.init` acceptance block: it runs before phase-1 initialisation, uses statics and parameters only, and its `try` covers the `backendFactory(...)` argument.
- `AppStore+CardActions`, `+ManagedActions`, `+ConnectedApps`, `AppStore.backend(for:)`/`notifyIfNeeded`: these are main-actor extensions on main-actor state. `any Conversation` has `id`, and `ChatMessage.metadata` is a mutable `@Published` on a class.
- Views: `ApprovalCard(request:decide:)` matches its existing use in `ChatView`. `MarkdownContent(message:actionTarget:)`, `DraftCardView`'s `message`/`index`, `SecretRequestPrompt` (Identifiable, for `.sheet(item:)`), `store.defaults` (internal `let`), `@FocusState`/`.focused` (macOS 14 target) all checked.
- Launchers: `AgentAppReleaseLauncher` (`@main @MainActor`, release only) and `AgentAppLauncher` (debug) are mutually exclusive by `#if DEBUG`, so there is one `@main` per configuration.
- Tests: `#expect(throws:)` closures calling main-actor methods sit in tests marked `@MainActor`, the same as the draft-send test. The heterogeneous `JSONSerialization` literal follows the existing `GrokRunSupport.swift:70`.

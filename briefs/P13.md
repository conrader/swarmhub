## Decisions for Konrad (defaults in bold)
- **D1 What "coding model" means.** Hermes has no coding-model role: nothing routes a message to a model by task type. Torvli can
  offer two real things: a *coding thread* (a fork of the chat whose turns run on the Coding model; client-side, started by a
  button) and the *sub-agent model* (what `delegate_task` children run on; set in the profile's config on the box, readable and
  settable by no app). **Accept both and name both in the UI. Coding done in the main chat stays on the Conversation model, and the
  copy says so.** If he wants no coding threads, the role is renamed "Sub-agent model" (display and guidance only) and Part D loses
  its coding-thread items.
- **D2 Box-side sub-agent pin.** May the orchestrator write the Coding default to `delegation.provider` + `delegation.model` in the
  `grok-*` profiles (reversible: numbered backup, `hermes -p <profile> config set`, one canary profile first)? Torvli never writes
  it. **Yes, after P13.0 passes; no fleet-wide write before that.** It is a second exception to PLAN's "no server-side config
  edits" (P9 was the first). If no, P13.0 and Part E are dropped and the Sub-agents line says "Set on the box" and nothing more.
- **D3 First-turn failure.** When the box refuses a chosen model as a chat starts: **a per-bot override stops that first send with
  a plain error (he chose that model for this bot; sending on another one is not what he asked for); the Torvli-wide default is
  skipped with a visible note and the message goes out on the box default (a default must never brick a bot, least of all one on
  another server).**
- **D4 Defaults are local and sticky.** The Torvli default lives in this install, not on the box. It is applied when a chat starts
  or on request and never moves a chat that has already started. A bot that has chatted keeps one long-lived session, so it changes
  only through an explicit Switch (one chat, or the previewed bulk step in Part D). A lock cannot be undone and turns the box's
  fallback model off. **Yes.**
- **D5 The coding model itself.** Torvli ships no model (PLAN). He picks it, ideally after P13.0 tried candidates. Evidence on his
  Codex account: `gpt-5.6-terra` works, `gpt-5.6-sol` answered once (a self-test probe, 2026-10-13), `gpt-5.4` and
  `gpt-5.3-codex-spark` are rejected, `gpt-5.3-codex` and `gpt-5.4-mini` are untried. One subscription window serves conversation,
  compaction and any coding model, and it returned 429 `usage_limit_reached` on 2026-09-23 and 2026-09-29.

## Goal
Konrad (2026-10-13): "a model for agent interactions and a separate model for coding tasks. This should be the default for all
agents, with the ability to override per agent." His agents are Torvli's bots. After P13 there are two model roles, each with a
Torvli-wide default and a per-bot override, resolved per bot as **override > Torvli default > box default**. The Conversation role is
fully client-side: Torvli remembers the choice and applies it with the session lock P3 and P11 already use. The Coding role is split
by what Hermes allows: coding threads are client-side; the sub-agent model is server-only, so Torvli shows what the box lets it
see, says plainly what it cannot, and gives the operator exact guidance. Settings → Models and the Overview state, per bot and per
role, what is set, where it lives and what actually ran. No provider credential is sent, read, stored or shown. The feature is inert
until configured: with no default and no override Torvli sends no extra request anywhere.

## What a client can and cannot set (recon 2026-10-13, read-only; confirm in `hermes-ref` before relying on it)

| Thing | Torvli can read it | Torvli can set it | Where it lives |
|---|---|---|---|
| Conversation model of one chat | session row `model` (not the lock); `runtime{}` of each turn | yes, once the session exists: `POST /api/sessions/{id}/model {model, provider}` | `sessions.model` + `model_config.browser_model_lock`; no unlock route |
| Box default model | `GET /api/model/options`, top-level `model` and `provider` | no | `model.default`, `model.provider` in the profile's `config.yaml` |
| Sub-agent (`delegate_task`) model | no | no | `delegation.provider` + `delegation.model` in the profile's `config.yaml` |
| Compaction, titles, vision, approval, routines | no | no (`POST /api/jobs` ignores `model`) | `auxiliary.<task>`, `cron.model`, job pins |

- **No config route.** `admin_config_rw` is a literal `false` in 0.20.5 and 0.21.7, and 13 candidate config routes answered 404 on the
  box. The dashboard has the writers (`PUT /api/config`, `POST /api/model/set`) but is a separate server that does not run on the
  box and also serves `/api/env`; nginx forwards only `/v1/`, `/api/jobs`, `/api/model`, `/api/sessions` and `/p/grok-`, so it is
  not reachable. It must never be exposed to Torvli.
- **No coding role.** `ContextProfile.model_hint = 'coding'` is declared and read by nothing, `smart_model_routing` is a dead key,
  `agent.coding_context` changes the prompt and not the model, and plugin hooks only observe. `delegate_task` has no model argument.
- **Delegation.** `delegation.provider` + `delegation.model` pin every child of the profile. Both empty means the child inherits the
  parent's runtime (provider, credentials, reasoning, and a session lock). `delegation.model` without `delegation.provider` binds that
  id to the parent's current provider, so a pin always carries both. `delegation.api_key` would be written to `config.yaml` in
  plaintext. Config is mtime-cached, so an edit applies on the next call without a restart (source reading, not exercised). Whether
  an agent delegates is the agent's choice: the 16 `grok-*` profiles have no `delegation` block, no delegate-child session and no
  `delegate_task` call in their state databases.
- **Return path of a background sub-agent.** Top-level `delegate_task` calls run in the background on the API server. On 0.20.5 the
  result returns through a self-POST to an unprefixed `/v1/chat/completions`: that turn runs on the box default, not the lock, and
  under multiplexing may resume the session in the default profile's store (inferred from `wake.py`, not reproduced). On 0.21.x the
  same file says async-delegation completions are never self-POSTed but written as a persisted `async_delegation_complete` delivery
  row, and the client owns the next turn (another source pass read an in-process wake on the default model). All of it is unverified
  on the box; P13.0 settles it.
- **Lock coverage.** A confirmed lock is honoured only by `POST /api/sessions/{id}/chat` and `/chat/stream`, the routes Torvli's
  native transport uses. `/v1/runs`, `/v1/chat/completions`, `/v1/responses` and routines (cron) do not read it. A body
  `model` on a locked session makes that turn non-locked, so Torvli's body stays `{input, instructions}`. A lock fails closed and
  turns the box's fallback chain off. `auto` auxiliary tasks (titles, vision, background review) follow the locked model; the
  box-pinned compaction does not.
- **Create, then lock.** `POST /api/sessions` accepts `model`, `provider` and `require_model_lock`, and answers 409
  `model_lock_unavailable` (before the insert) for an unroutable pair, 409 `session_exists` for a duplicate id. `HermesBackend`'s
  `createSession` treats every 409 as "exists" (`HermesBackend.swift:144`), so a lock in the create body would turn a refused model
  into a phantom session id. Create plain, then `POST …/model`.
- **Standing selection.** The first turn stamps `sessions.model`; from then on that string pins the session and a changed
  `model.default` reaches no started chat. Every session on the 16 `grok-*` profiles already carries today's default. A fork copies
  the model string, the cached system prompt and the transcript, not the lock; a lock clears the cached prompt so it is rebuilt
  (Torvli resends `instructions` every turn, so the persona is unaffected). `hermesSessionID` is written once and never reset, so a
  bot that has chatted is changed only by an explicit lock.
- **`runtime{}`.** `{provider, model, route_source, requested, model_lock}` rides `run.started`, `assistant.completed` and
  `run.completed` of the session stream in both versions; Torvli ignores it today. It can be `{}` (0.21.x replays).
- **Box state.** 23 profile configs; conversation `gpt-5.6-terra` on `openai-codex`, compaction pinned to `gpt-5.6-luna`, one fallback
  entry; no `delegation`, `model_routes` or `cron.model` anywhere; the `delegation` toolset is enabled. The 16 `grok-*` configs are
  byte-identical copies and Hermes has no default-to-profile inheritance, so "a default for all" on the box means writing every
  file. The agenthut layer overlay writes the root config only (compaction, fallback, context length); it carries no `model.default`
  and no `delegation.*`.

## The two roles
- **Conversation** is the (provider, model) of the agent that serves each turn of a chat. Torvli's hold on it is the per-session lock.
  Side effects the UI states: an unpinned sub-agent and `auto` auxiliary tasks follow it.
- **Coding** has two surfaces and one setting.
  1. *Coding thread* (client-side): "Code in thread" forks the chat and locks the fork to the Coding choice. The turns Torvli sends
     in that thread run on it. Not covered: turns Hermes starts itself after a background sub-agent, routines, anything started
     outside Torvli. Copy never says that sub-agents in the thread run on the Coding model; source says an unpinned child inherits
     the locked parent, and that stays unproven until P13.0.
  2. *Sub-agent model* (box-side): `delegation.*`. Torvli shows whether delegation is on for the bot (`/v1/toolsets` row
     `delegation`) and, after Part E, the model a sub-agent was last seen to use. It cannot read the pin.
  Code the agent writes or runs itself in the main chat uses the Conversation model. Torvli does not classify messages.
- **Precedence**, per role, resolved when applied and never copied into the bot. A bot's setting has three states: *inherit*
  (follow the Torvli default), *box* (opt out of the Torvli default) or a (provider slug, model id).
  - Conversation: the bot's choice; else the box default if the bot opted out; else the Torvli Conversation default; else the box
    default.
  - Coding: the bot's choice; else "same as conversation" if the bot opted out; else the Torvli Coding default; else "same as
    conversation".
  "Box default" is the profile's `model.default` when the chat starts (the first turn stamps it on the session). The sub-agent pin
  is a separate, box-side value that Torvli cannot read; the Coding setting never claims to show it.

## Design
**Storage.** Only a provider slug and a model id (≤200 characters, no control characters) are ever stored; never a name, URL or key.
- `StoreFile.modelDefaults {conversation, coding}`: both `ModelChoice?`, `decodeIfPresent`, version stays 2, a v1 bare-array store gets
  an empty value, and a defaulted init parameter keeps `StoreFile(bots:groups:)` compiling. Not `UserDefaults`: `--e2e` and headless
  stores use `.standard` defaults and would pin every self-test session, while a `StoreFile` field is empty in their temp stores.
- `Bot.modelSettings: BotModelSettings?` `{conversation, coding}`, each a `ModelSetting` (inherit, box, choice; an unknown kind
  decodes as inherit). `nil` when everything inherits, so untouched bots encode byte-identically. Same idiom as `computerURL` and
  `hermesModelLock`: a property with a `nil` default (the long init line stays untouched), one `CodingKeys` case, one decode, one
  encode. If P12's `OpenClawBinding` makes the rebase painful, fall back to a sidecar `[UUID: BotModelSettings]` in `StoreFile`
  cleaned in `AppStore.delete`.
- `HermesModelLock.origin: LockOrigin?` (`bot`, `torvliDefault`, `coding`; `nil` = picked by hand or before P13) so the Overview can
  say who pinned a chat and the bulk step can keep hand picks; `nil` keeps P3's equality assertions true. `ChatThread.role:
  ModelRole?` and `ChatThread.modelLock: HermesModelLock?`, `decodeIfPresent`.
- `Models/ModelPolicy.swift` is pure and `Sendable` (no SwiftUI, no network): `ModelRole`, `ModelChoice`, `ModelSetting`,
  `BotModelSettings`, `ModelDefaults`, `ModelSource`, and `resolve(role:settings:defaults:)` → `(choice?, source)`. It is the
  backend-neutral seam OpenClaw can use later.

**Applying.** Torvli applies a resolved pair (never "box default", which sends nothing) (1) at a main chat's first send (the create
site in `AppStore.send`), (2) at a group member's session creation (`AppStore+Groups`), (3) on "Switch this chat", and from Part D
(4) on "Switch existing chats…" and (5) on threads. Never on reviewer sessions (`AppStore+Approvals.swift:91` shares
`createSession`), routines, or a chat that started before the default changed. Apply at store level, after the session exists, with
the existing `try backend(for: bot) as? HermesBackend` guard; never inside `HermesBackend.createSession`. Sequence at chat start:
load or reuse the bot's capabilities and model options (P11's `load`; the Overview may be closed, so the apply path asks for them
itself) → `POST /api/sessions` (body unchanged) → `GET /api/sessions/{id}` and apply only when its `model` is nil or the virtual
alias (an old session returned by the 409 "exists" path keeps its standing model) → refuse unless the pair is in this bot's own
loaded list (P11's listed-only rule, exposed as a pure function) → `POST /api/sessions/{id}/model {model, provider}` → record the
`HermesModelLock` with its origin → save → send. The chat body carries no model field.
- **Gating.** `HermesCapabilities.sessionModelLock && modelOptions`, a loaded list, the session read (`session_resources` not false)
  and the native-sessions transport. An absent flag follows `HermesCapabilities.supports` (a listed endpoint, or no endpoint list,
  means try); 404/405 means the route is absent. Do not use `HermesBackend.features()` (absent = unsupported). The legacy transport
  has no sessions and sends `"model": "hermes-agent"`, so the feature is native-sessions only and says so. Every route used exists
  in 0.20.5 and 0.21.x; no version string appears in code. The versions differ only where this feature reads defensively:
  `runtime{}` can be `{}`, a delegation completion can be a delivery row, and P11 covers the catalog differences. Coding threads
  also need `session_fork` (`canFork`).
- **Failure.** Per D3. Both paths go through `BotInfoCache.describe`, so a bot key never reaches a note. A refused override leaves
  `hermesSessionID` unset so the next send repeats safely (in a group, the member's turn is skipped with the existing "was
  skipped" system note); a skipped default posts one system note in the chat (native turns send only the last user message, so notes
  never reach Hermes), sets `modelError`, and offers "Switch this chat".
- **Per-bot validation, never at save time.** Bots can sit on different servers or profiles with different catalogs. A stored choice
  the bot's own list lacks is skipped with its reason and never sent.

**Settings → Models** (one `Pane` case, SF Symbol `cpu`; `Views/SettingsModelsPane.swift`). Static, no animation.
- Caption: "Torvli remembers these choices and applies them when it starts a chat. It does not change your box's own settings."
- "Models from: [bot]" picks the reference bot whose profile catalog feeds the pickers (a view preference). Pickers are P11's
  `ModelPickerModel` rows plus a leading row ("Box default", "Same as conversation", "Use Torvli default") and a role label.
- **All bots**: *Conversation model* [Box default ▾] ("Used for chats, group chats and threads Torvli starts.") and *Coding model*
  [Same as conversation ▾] ("Used for coding threads. Sub-agents use whatever the box sets."). When both resolve to the same
  supplier: "Both use <supplier>; they share its usage limit" (from supplier slugs, not measured).
- **Per bot**: one row per Hermes bot (grouped by server, as `usageProfiles` does) with "Conversation" and "Coding threads", each
  with the resolved value and its source tag (`this bot`, `Torvli default`, `box default`, `same as conversation`), and **Edit…**,
  which opens the bot's editor sheet as Auto-review does. OpenClaw bots are listed greyed, "Managed in OpenClaw".
- **Set on the box (read-only)**: the box default per bot ("same on N of M" or "differs"), sub-agents, compaction, routines; one line
  each, with "Set on the box. Hermes doesn't let apps read or change it." for all but the first.
- An explicit **Load** (the Usage pattern), concurrency ≤4, results into the shared `BotInfoCache` through P11's `load`; if `load`
  cannot fetch a subset (capabilities, options, toolsets, session row; no skills), add that parameter there instead of a second
  loader. Opening the pane fetches nothing.

**Bot editor** (`BotEditorView`, a Models section in `Views/BotModelSettingsSection.swift`, Part B): both roles, each "Use Torvli
default (<value>)", "Box default" (Conversation) or "Same as conversation" (Coding), then the bot's models. A new bot with no
profile yet gets only "Use Torvli default".

**Overview** (P11's Model section; `Views/ModelRolesReadout.swift`, hooked in with one line): P11's chat line and picker stay and
keep meaning "this chat only". Below them three lines: "Conversation: <model> · <supplier> · <source>", "Coding threads: …" and
"Sub-agents: Set on the box. Hermes doesn't let apps read or change it." plus the delegation toolset state, and nothing else until
Part E. When the resolved Conversation choice differs from what the chat runs: "This chat runs A; this bot's default is B.
[Switch this chat]". When the resolved choice is the box default but the chat is locked: "Hermes can't unpin a chat; this pins it
to the box's current default (X)." Each line has the accessibility label "<role>, <model>, <supplier>, <source>".

**Chat** (Part D): **Code in thread** beside "Reply in thread" (one thread per message, as today), shown only when Coding resolves to
a concrete pair that differs from the model the chat runs; the thread header reads "Coding · <model>" instead of "Thread".

**Reasons.** One enum `ModelRoleReason` of fixed one-line strings, each pinned by a test, beside P11's states (reused verbatim):
no lock ("This box can't switch a chat's model, so Torvli can't apply a model here."), no list ("This box doesn't list its models, so
Torvli can't check a choice before using it."), no row ("This box can't report a chat's model, so Torvli can't tell whether the
chat is new."), legacy ("This box only has the older chat API, which has no per-chat model."), no fork ("Coding threads need
conversation forks, which this box doesn't offer."), not offered ("<model> isn't offered by this bot's profile."), permanent ("Hermes
can't unpin a chat, and a pinned chat has no fallback model."; next to every control that pins), box only, sub-agents off
("Sub-agents are turned off for this bot."), OpenClaw ("Managed in OpenClaw."). A control that cannot work stays visible, disabled,
with its line.

**Headless.** `--render-snapshot` prints one more line per `--bot` from the same pane model: names and counts only, for example
`Jarvis: roles conversation gpt-… (box default) | coding threads same as conversation | sub-agents on, set on the box`.

## Rules that bind every part
1. Torvli never writes box config and never adds a client for a route that does not exist. The only model write is the existing
   lock call `{model, provider}`, always on the bot's own `/p/<profile>/` with its own Keychain key; the create and chat bodies stay
   as they are.
2. Persist and send only slug and id strings. Catalog parsing stays P11's allowlist (`key_env`, `auth_type`, `api_url`, `warning`,
   `usage` are never read). Server-supplied strings render verbatim and are never put in a shell command (Part E excepted, with
   its allowlist).
3. Inert until configured: nothing configured means no extra request, and P3's `BotInfoTests`, P8b's `E2ETests` and the existing
   `--e2e` steps run unedited. Edit an existing assertion only where behaviour changes on purpose and name each edit in the report.
4. Create plain, then lock (see above). Never add `require_model_lock` to the create body and never put `model` in a chat body.
5. No hardcoded provider or model names anywhere under `Sources/`; a test greps for the fixture names too.
6. Swift 6 strict concurrency (`Sendable` value types for policy; `Bot` is a non-`Sendable` class). New code is formatted normally
   (≤140 columns). Static text, no spinners, no animation.
7. Production-line caps (new plus edited, tests excluded): A 400, B 300, C 200, D 350, which is about +15 % on today's 8,210; E adds
   up to 150. A part that would pass its cap by a fifth stops and says so; do not trim tests to fit.

## Risks
- **Coding is not a Hermes role.** The pin covers every delegated task, not only code; the main chat's own edits stay on the
  Conversation model; whether an agent delegates is its call (none of the 16 `grok-*` profiles ever has), so the pin may rarely fire.
  The coding thread is the only deterministic path and it needs a gesture. The copy says all of this.
- **The delegation return path is unproven** (0.20.5 wake: unprefixed self-POST, runs on the box default, may resume the default
  profile's session; 0.21.x: a persisted delivery row Torvli's history does not treat specially). Until P13.0 passes, nothing
  claims sub-agents work.
- **Locks are sticky and fail closed.** No unlock route; the box's fallback chain is off; "box default" cannot be restored on a
  locked chat, only re-pinned to today's default; a changed `model.default` reaches no started chat. A fail-open skip after one
  transient error leaves that chat on the box default until someone switches it.
- **Listed is not routable.** The lock checks routability only. The Codex list holds ids the account rejects (`gpt-5.4`,
  `gpt-5.3-codex-spark`; 5 of its 8 listed ids are absent from the live catalog), so a pinned pair can pass the POST and fail on the
  next turn. Part C's "ran on" note and the one-tap recovery arrive before the bulk step for that reason.
- **Quota coupling.** A coding model on the same subscription shares its window with conversation and compaction (429s on
  2026-09-23 and 2026-09-29). Torvli can only hint when both roles share a supplier.
- **Lock coverage is narrow** (session chat routes only); `auto` auxiliary tasks and unpinned sub-agents move with the lock. A
  compaction rotation would create a child session without the lock; the box runs `compression.in_place`, so not today, and the
  "ran on" note would show it.
- **A Torvli default is local.** Telegram, WhatsApp, the CLI, cron and other Macs never see it; there is no sync.
- **0.21.x is source-read only** (no live payload, canary red at last note): `runtime{}` may be `{}`, delivery rows are new, and
  `delegation.fallback_providers` exists there. All must degrade to "no state".
- **A fork ends its source session as `branched`** (P4's behaviour); frequent coding threads may expose edge cases. Each fork copies
  the whole transcript, so the coding model sees the chat and its context cost is paid.
- **Size and collisions.** About +1,250 production lines and ≈1,000 test lines against 8,210 and 2,995; four parts, two of them
  gated on a live proof. P10, P11 and P12 edit the same files; a late rebase is the likeliest delay.
- **Unseen.** Menu and sheet rendering, and the Swift 6 build, are checked only on the MacBook and by Konrad opening the pane.

## Out of scope
- Writing any box config from the app, and any client for a route that does not exist. A read-only roles report from the box (for
  example `delegation.*` in a capabilities or options payload) needs an owner (a fleet patch or an upstream request) and a
  capability flag first; until then Torvli builds nothing for it.
- Classifying messages into coding and conversation, per-turn model switching, a composer chip, any "smart routing".
- Auxiliary models (compaction, titles, vision, approval), routines' and cron's model, a Reviewer role, `model_options` (reasoning
  effort, service tier), fallback-chain edits, MoA, kanban's per-task model, a dedicated coder profile, installing coding CLIs.
- The doctrine that makes an agent delegate (a skill or SOUL on the box), apart from P13.0's optional check.
- Unlocking a chat (no route), moving started chats automatically, syncing defaults across Macs, "Use X for new chats with this bot"
  after a manual pick (a later convenience).
- OpenClaw: it has native defaults and per-agent overrides (`agents.defaults.model`, `subagents.model`) and an admin write RPC; P12b
  can add them behind the same policy types. Until then its rows read "Managed in OpenClaw".

# P42 — Watch a bot work for another bot

Konrad, 2026-10-15: "If infra is doing something because other bot issued work - we need to see what its doing - also
avatar needs to animate to show that its busy". Builds on P41 (bot-msg parsed from the full command, recipient
"Working… · message from <sender>", reply on the sender's chip, persisted seen marks, arrival line). Starts after P41 merges.

## Facts
- A bot-msg run lives in the recipient's Hermes session `swarmhub-from-<sender>` (source api_server, title "From <sender>"),
  started by bot-msg's own curl (`POST /api/sessions/<id>/chat/stream`), not by SwarmHub. The session's rows (user message,
  assistant tool calls, tool results, final reply) are readable through the same session API SwarmHub uses for history
  (live case: Infra, 44 rows in 2.5 min, 2026-10-15 19:47–19:50).
- Avatars already have a working state (`BotAvatarState.working`, `AvatarMarkViews.swift` motion `.working`), used today
  only for SwarmHub's own turns.

## Build
1. **Live work card.** While a recipient works on a bot message (from the sender's running bot-msg step, or detected by
   polling: the From-<sender> thread changed and its last row is not a final assistant reply), poll that thread every 2 s
   (back off to 10 s after 1 min without change; stop at the final reply or 30 min) and show in the recipient's chat a
   "Working for <sender>" card whose steps unfold like SwarmHub's own turns (P29 Steps row: commands, files, web reads,
   skills), then the reply. Reuse the existing step/activity parsing of history rows; no new server calls beyond the
   session history read.
2. **Avatar and sidebar.** The recipient's avatar plays the working motion in the sidebar and chat header for the whole
   time, row text "Working… · for <sender>", back to idle at the end. Several bots can be working at once (P39).
3. **One conversation.** "Open conversation" shows the whole exchange: the sender's request, the recipient's steps, its
   reply — and further messages between the two in the same thread.
4. **Queued messages (`--no-wait`) and restarts:** detection by polling covers work SwarmHub didn't see start; after a
   restart a thread changed within the last 30 min that is still mid-run shows the live card again.
5. Load: at most one live poller per thread, none for bots on a disconnected connection; P39's turn limits don't apply
   (these are reads, not turns).

6. **The other route: `hermes -p <bot> chat --oneshot … -q '<text>'`.** Live case 2026-10-15 20:23 (Konrad: "reactor chat -
   nie widac komunikacji z jarvisem mimo ze twierdzi ze zapytal go o cos"): Reactor has no SwarmHub skills, so it ran
   `hermes -p grok-jarvis chat -Q --oneshot --max-turns 12 --run-budget 150 -q 'Wiadomosc od grok-reactor …'` in its
   terminal; Jarvis got a session `20261015_202332_77e6a5`, source `oneshot`, title = start of the text, 22 rows, and
   Reactor reported "Zapytałem Jarvisa…". Nothing showed in SwarmHub (bot-messages.log has no entry; the app lists only
   `source=api_server`). Recognise this command in a step exactly like bot-msg (sender = the stepping bot, recipient =
   `-p`), show the same live card/avatar for the recipient, and find the recipient's session by listing its sessions with
   `source=oneshot` started after the step began; the conversation sheet shows it.
7. **Every bot gets the messaging skill.** Only Jarvis has SwarmHub skills (Infra, Reactor none). In Settings and on the
   manager's banner offer "Install SwarmHub skills on all bots" (swarmhub-messages, swarmhub-feedback; the manager writes
   them into each profile, one confirmation for all), and show per bot which are missing. Bots that have it use bot-msg.

8. **Every wake is visible in the woken bot's chat** (Konrad, 2026-10-15: "czy wiadomosci miedzy botami robia wake?" …
   "i czy ewentualnie rutyny albo ogolnie inne rzeczy moga" … "tak, zapisz i buduj w tej kolejnosci"). One rule: whatever
   starts a turn the user didn't type — a message from another bot (both routes), a routine run (its `cron_<job>_<time>`
   session), a late reply (below) — shows in that bot's chat as a line "Woken by: <Jarvis | routine <name> | reply from
   <bot>>", then the live steps (item 1) and the result, with the avatar working throughout. Routine runs: while a job's
   run is in progress (P43's running state), show its cron session live the same way; P43's finished card stays the end.
9. **Late replies wake the sender.** Today `bot-msg` waits `--wait 300` s; if the recipient takes longer (exit 124) or the
   sender used `--no-wait`, the reply lands only in the recipient's session and the sender is never told. Change the
   swarmhub-messages skill (version bump; installed by the manager like other SwarmHub skills): in those two cases a
   background follow-up waits for the recipient's reply (up to 30 min) and delivers it to the sender as a new message in the
   sender's session `swarmhub-from-<recipient>` ("[Reply from <recipient> via SwarmHub] …"), which starts the sender's turn
   so it can finish and tell Konrad. No loops: a message marked as a delivered reply never triggers another follow-up, and
   the skill text tells bots not to answer it back to the recipient. Logged in bot-messages.log as `late-reply`.
   Tests: the script in a temp HOME with a stub gateway (slow recipient → exit 124 → follow-up delivers once; --no-wait →
   delivered once; a delivered reply never re-delivers); the app shows "Woken by: reply from Infra" in Jarvis's chat.

## Tests and done means
Oneshot command parsed (the live command above) and its session found; install-on-all-bots sends one manager request covering every profile without the skills. Fake server with a thread whose rows grow over time: card appears, steps unfold in order, reply ends it, avatar state
working → idle; back-off and 30-min stop; detection without a sender step; restart mid-run; two recipients at once; no
poller for a disconnected connection. Renders: Infra's chat with the live card mid-run; the sidebar with Infra working for
Jarvis (avatar working frame); the conversation sheet. One full `swift test` green in the run + the verify pass; files ≤ 500.

# P27 — SwarmHub skills installed into bots (no improvising), plus the model recipe

Konrad 2026-10-14, after Jarvis spent 5+ minutes improvising "switch all agents to 6.1 sol" (48 KB stock skill read,
~10 exploratory calls, ~90 slow `hermes config set` runs, a 180 s tool timeout, 11 of 23 profiles done):
"yes add the model recipe and ship it" · "Maybe we should install instructions to bots so that we won't improvise" ·
"and just notify that this needs to be built" · "we are not talking about changing hermes" · "but creating
tools/skills inside swarmhub".

So: skills are authored and versioned INSIDE SwarmHub (this repo), and SwarmHub installs them into a bot's own
profile as ordinary Hermes skill files (`SKILL.md`, the same thing a user installs by hand). Hermes itself is never
changed, patched or configured. When a bot's installed copy is missing or older than SwarmHub's, SwarmHub notifies and
offers Install. P22's token rule stays: nothing big rides on ordinary turns.

## Decisions
- **D1 Model recipe** in `Resources/BotManager/manager-hermes.md` (keep it ≤ ~4 KB): "Change the model (one bot, some,
  or all): ask first, naming model, provider and bots. Run it in the background so it is not cut off:"
  ```
  export MODEL=<model> PROV=<provider, e.g. openai-codex>
  nohup sh -c 'for N in "$@"; do hermes -p "$N" config set model.default "$MODEL" >/dev/null && hermes -p "$N" config set model.provider "$PROV" >/dev/null && echo "$N ok" || echo "$N FAILED"; done; echo DONE' sh <names> > ~/.hermes/swarmhub-model.log 2>&1 &
  ```
  `<names>` for all bots: `default $(ls ~/.hermes/profiles | grep -E '^[a-z0-9][a-z0-9_-]*$')`. The sub-agent / coding
  model only when asked: same loop with `delegation.model` / `delegation.provider`. Then `cat ~/.hermes/swarmhub-model.log`
  until DONE (~10 s per bot) and report ok/FAILED per bot. Never edit config.yaml by hand. Say that SwarmHub chats with
  their own chosen model keep it (changed in that chat's model menu). (`hermes -p <p> config set` is stock; the gateway
  rereads config.yaml by mtime, no restart.)
- **D2 Intent.** `ManagementIntent` also matches model requests (EN+PL): a change verb (switch, change, set, move,
  use, upgrade, przełącz/przelacz, zmień/zmien, ustaw) + a bot noun or all/every/wszystkie/wszystkich + a model word
  (model, models, modelu, modele) or a model-like token (contains `gpt`, `sol`, `terra`, `claude`, `opus`, `sonnet`,
  or `\d+\.\d+`). "can you switch all agents to 6.1 sol ?" must match; ordinary chat must not (extend the existing
  negative list). Manage bots menu gains "Change model…" ("Change the model of <bots> to ").
- **D3 Skill library.** `Resources/Skills/<name>/SKILL.md` (+ optional `references/`), copied by Package.swift
  (`.copy`) and both build scripts like `Resources/BotManager`. Frontmatter: `name`, `description`, `version`
  (semver), `metadata.swarmhub.source: swarmhub`. First entry `swarmhub-manager`: its body is rendered from
  `manager-hermes.md` (one source of truth, no copy) with placeholders filled for the target profile; its description
  says when to use it (creating/changing/retiring bots, their instructions/avatars/descriptions, changing models).
  A `SkillLibrary` type lists bundled skills and renders one for a bot.
- **D4 Install through the connection's manager** (no SSH, no new server API): Install sends the manager one
  management turn: for each skill, `mkdir -p <skills>/swarmhub/<name>` and `cat > .../SKILL.md <<'SWARMHUB_EOF'` …,
  where `<skills>` is `~/.hermes/skills` for `default` else `~/.hermes/profiles/<p>/skills`; Konrad pressing Install
  IS the yes (the turn says so); the reply ends with
  `{"op":"skills_installed","bot":"<profile>","skills":[{"name":"…","version":"…"}]}`. New op in `SwarmhubBlock`;
  the app records installed name→version per bot (persisted). Only skills from the library; content is never taken
  from the reply. A bot without a manager on its connection shows "Needs a manager bot to install".
- **D5 Notify.** A bot is "needs install" (missing) or "needs update" (recorded < bundled). Shown: (a) a small banner
  in the manager's own chat when its `swarmhub-manager` needs install/update, with Install / Not now (Not now hides it
  until the next bundled version); (b) bot editor → Advanced → "SwarmHub skills": per skill name, version, state,
  Install/Update. Plain words in simple copy ("SwarmHub's instructions for <bot> need installing").
- **D6 Tokens.** When the manager's `swarmhub-manager` is recorded at the bundled version, management turns attach a
  one-line pointer ("Use your swarmhub-manager skill for this; end with a swarmhub block.") instead of the full text;
  otherwise the full text as today. Ordinary turns: nothing, as today. Hermes request bodies otherwise unchanged.
- **D7 Confirm when possible.** When the connection's `GET /v1/skills` works, opening the editor's SwarmHub skills
  section refreshes the record from it (name + version of skills whose category is `swarmhub`); a 500 (stock 0.22.0)
  or other failure keeps the recorded state silently.
- **D9 Show what the bot is doing** (Konrad: "why I was not notified what bot is doing … he was just thinking").
  Cause: `HermesBackend` already turns `tool.started/completed/failed/progress` and `hermes.tool.progress` into
  `.status(...)` (`HermesBackend.swift:374,384`); `AppStore+Turns.swift:38` stores only the latest, only while the
  reply is empty, in `metadata["status"]`; no view shows it for a normal reply (`MessageView.swift:79` = bare spinner).
  Build: (a) keep an ordered activity list per streaming assistant message (tool name, a short preview of its argument
  or message when the event carries one — truncated to ~80 chars, redacted with the existing redaction helpers, never
  a key — start/finish time, failed flag); (b) while streaming, under the reply a live line "Running <tool> · step N ·
  1 m 12 s" (also once text has started); (c) after the turn, a folded "12 steps · 4 m 52 s" row that expands to the
  list; persisted with the message (bounded, e.g. last 50 steps); (d) a turn still running after 60 s with no new text
  shows the current step in the sidebar row's preview line ("Working: terminal …"). First record which fields the
  real stream carries: capture one live turn's event names + keys (no values) via the existing e2e path or a fake, and
  base previews only on fields that exist; tests use fixtures of those shapes. Same for OpenClaw tool events if P12
  maps any. Plain words in simple copy ("Working…", "Running a command", "Reading a file").
- **D8 OpenClaw** unchanged in this phase (P26 on-demand text); note as follow-up in PLAN.

## Tests (Swift Testing, fakes only)
1. Intent: the Jarvis sentence and PL equivalents match; extended ordinary-chat negatives don't.
2. Template: model recipe present; no `{{` left after rendering; size bound; no secret-reading commands.
3. Library: bundled list; rendered SKILL.md has valid frontmatter, version, profile placeholders filled, body equals
   the rendered manager text; resources are in the built bundle (path candidates like `BotManagerText`).
4. Install turn: carries exactly the library content in heredocs to the right path (default vs named profile);
   `skills_installed` block records versions; content in the reply is ignored; another connection's bots untouched.
5. Notify: missing/outdated/current states; banner Not now persists per version; editor rows.
6. Tokens: installed-current → pointer line only; missing/outdated → full text; ordinary turn → nothing.
7. `/v1/skills` refresh: 200 updates the record; 500 leaves it.
8. Activity: event fixtures → ordered steps, previews redacted/truncated, live line text + elapsed, folded summary after the turn, persistence bound, sidebar "Working:" after 60 s.

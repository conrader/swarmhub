# P9 — Grok history on Konrad's box

Read `PLAN.md` first; its standing constraints apply. Starts only after Konrad accepts this brief. It writes to his live box,
so follow the canary order, keep every backup until he signs off, and treat a red check as a full stop.

## Goal
Each `grok-*` bot on Konrad's box can find its own Grok history (`session_search`), and Hermes clients can list it as an
archive. Torvli shows one archive per bot, never two copies. Nothing that already exists on the box changes.

## Facts (recon 2026-10-13, read-only)
- Box 195.201.33.222 runs Hermes 0.20.5 from `/opt/hermes-core/releases/0.20.5/src`. Disk `/` is 38G, 2.2G free (94%).
- Each profile has its own `state.db` at `/home/hermes/.hermes/profiles/grok-<slug>/state.db` (grok-jarvis is 360K, 5 sessions,
  14 messages). Its `schema_version` is 31, while the ref source has 26, so never write raw SQL.
- The writer to use is the installed `SessionDB`: `create_session(id, source)` (`hermes_state.py:4714` in the ref) and
  `append_messages_batch` (`:9411`). FTS tables are filled by AFTER INSERT triggers.
- `session_search` hides only `kanban`, `subagent` and `tool` sources (`tools/session_search_tool.py:46`), so `grok-import` is searchable.
- `POST /api/sessions` coerces unknown sources to `api_server`, and no endpoint appends messages, so the API route can't do this.
- Profiles already hold `memories/grokbot-history.{md,jsonl}` (the last 10 messages). Leave those untouched.
- Source data: `~/Documents/Torvli Grok Export/` on the MacBook has 6,843 messages for 16 bots plus the group chat, all from
  seq 1. Secrets were already redacted by the exporter.

## Part A — server import (runs from OVH; box ssh with the operator key)
1. **Recon.** On the installed release, read the `SessionDB` signatures (create, append, delete), the columns of `sessions` and
   `messages`, how `GET /api/sessions` and `session_search` treat `source='grok-import'`, the file owner of each target
   `state.db`, and that at least 1 GB is free. Abort if any of these differ from the Facts above.
2. **Script** `scripts/hermes-import-grok.py` (≤500 lines; stdlib plus the box's own `hermes_state` via `--hermes-src`):
   - Flags: `--bundle <dir> --profile <name> --dry-run | --apply | --rollback`.
   - **Session layout:** one session per bot per calendar day (Europe/Warsaw). Session id `grok-import-<bot8>-<yyyymmdd>`,
     title `Grok archive · <Bot> · <date>`, source `grok-import`. Keep the original timestamps.
   - **Messages:** roles are user or assistant. Skip events and notices.
   - **Group chat:** prefix each message with its speaker (`[DMT] …`) and store it in both DMT's and Achilles's profiles.
   - **Re-runs:** idempotent; skip any session id that already exists.
   - **Rollback:** `--rollback` deletes only `grok-import` sessions.
   - **Output:** counts only, never message text.
   - **Tests:** unit tests on OVH against a stub `SessionDB` and a schema-only fixture, with no real data in the repo.
3. **Transfer.** Copy the bundles MacBook → OVH scratch → box `/home/hermes/grok-import/` (0700, owner hermes). Delete
   them after Konrad signs off.
4. **Dry run** on the box against a `sqlite3 .backup` copy of Rapper's `state.db` (the smallest bot): `--apply`, check counts
   and FTS hits, `--rollback`, confirm it's back to the original, then delete the copy.
5. **Canary: Rapper.** Back up every target `state.db` with `sqlite3 .backup` into `/root/grok-import-backup-<ts>/` (a few MB).
   Run as user `hermes` with the box's venv, because root-owned `-wal`/`-shm` files would lock the bot out. Import Rapper. Verify:
   - counts read back with `SessionDB`;
   - the owner is unchanged;

   - one self-test turn in a new `torvli-selftest-` session: "[Torvli self-test — reply briefly, take no actions] Use

6. **Roll out** the other 15 bots plus the group. For each profile, the messages read back must equal the export's count.
   Repeat the recall self-test on Jarvis, the biggest bot. Then `--check-bots` must show 16/16.

## Risks
- **Schema drift:** use only the installed `SessionDB`, and do the dry run on a copy. A 0.21.7 upgrade migrates these rows like any others.
- **Live writes:** `SessionDB` uses WAL with `BEGIN IMMEDIATE`, the same as Hermes's CLI, so the gateway needs no restart.
- **Stale facts resurfacing:** the original timestamps keep these rows ranked as old, and the titles mark them as an archive.
- **Disk:** the import adds a few MB. The box's 94% disk is still a separate open item for the 0.21.7 canary.

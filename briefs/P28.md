# P28 — Steer that actually lands

Open-work row "Steer is accepted but ignored" (e2e step b, every run on 2026-10-14: HTTP 2xx, reply unchanged).
Cause, from Hermes 0.22.0's own source on Konrad's box (read-only):
- `POST /v1/runs/{id}/steer` (`gateway/platforms/api_server_runs.py:1219`) → `agent.steer(text)`
  (`agent/interrupt_control.py:267`): "Queue user text for delivery as its own user row **after the current tool batch
  finishes** (no interrupt)". 409 `run_not_accepting_steer` when the run is not `running`.
- A turn that is only generating text has no tool batch, so the steer is never delivered in that reply (the e2e's
  "count 1..20" turn). `redirect()` (cancel the model request, append the correction, retry) exists in the agent but
  has no HTTP route. Vanilla Hermes stays untouched: the fix is in SwarmHub.

## Decisions (defaults; Konrad: "Build all, defaults")
- **D1 Two behaviours, chosen by what the turn is doing** (P27's activity steps tell us):
  - a tool step is running (a `tool.started` without its `completed/failed`) → steer as today; the steer bubble says
    "Delivered after the current step" until the next step/`run.steered` evidence, then "Delivered";
  - no tool step running (text streaming, or thinking) → **Stop and send**: request Stop for the run (existing stop
    path), keep the partial reply (P16 keeps partials, marked stopped), then send the steer text as the next user
    message in the same session with a one-line lead the model sees: "(Correction while you were answering:)". The
    steer bubble says "Stopped the answer and sent your correction".
  - If Stop fails, fall back to the queued steer and say so in one line.
- **D2 Copy.** Composer placeholder while streaming: "Add to this answer…" (unchanged if it already says so). A
  one-time caption under the composer the first time a steer is sent: "Corrections land after the current step, or
  stop the answer and continue." Plain words.
- **D3 OpenClaw.** P12 maps steer to `chat.send` with `queueMode:"steer"`; keep it, but apply the same Stop-and-send
  rule when the Gateway reports no tool activity, if OpenClaw's steer has the same "after the tool batch" semantics
  per its docs (`docs/` in the P12 reference); otherwise leave OpenClaw unchanged and note it.
- **D4 e2e step b.** Becomes two checks: b1 "steer during text" expects the stopped partial + a new reply that obeys
  ("E2E-STEER"); b2 "steer during a tool step" (prompt that makes the bot run one cheap tool, e.g. read a tiny file in
  its own workspace or `echo`) expects the steer to arrive after the step. PASS only when the reply shows the effect;
  "accepted but ignored" becomes FAIL.

- **D5 Order on screen** (Konrad 2026-10-14 18:5x: "Jarvis right now is not replying to me" — he had replied; his
  answer sat ABOVE Konrad's steer bubble because the bubble is appended at the end while the reply keeps streaming
  into the assistant message created before it). When a steer is delivered during a turn (queued or via Stop-and-send),
  the transcript must read in true order: the reply text produced before the steer stays in the earlier assistant
  message (marked part 1, no extra chrome), the steer bubble follows, and every token after delivery streams into a NEW
  assistant message below the bubble (same turn, same run; one finishTurn; activity steps continue on the new message).
  The saved store, history reload (`HistoryReconciler`/messages order from the box) and group chats keep this order.
  Tests: a fake stream with a steer delivered mid-reply produces [user, assistant(part before), steer, assistant(rest)];
  reload from box history keeps it; the sidebar preview shows the newest assistant text.
- **D6 401 noise.** Since 18:45 UTC on 2026-10-14 Konrad's 0.4.7 sent `GET /p/grok-jarvis/v1/capabilities` with a key
  the box rejects (pairs, every 25–50 s) while every other call for Jarvis used the right key. Find which code path
